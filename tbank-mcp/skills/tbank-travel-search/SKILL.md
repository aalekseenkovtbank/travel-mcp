# Поиск: поезда, самолёты, отели, маркетплейс

Если запрос посвящён только выбору отеля, перейди в `tbank-hotel-search`: там
описаны актуализация шорт-листа и самостоятельная страница отелей. Для полной
поездки дополнительно прочитай MCP resource
`travel-nova://instructions/travel-output-modes`: HTML через `trip-page/v2` и
`render_travel_page()` является режимом по умолчанию, chat-режим включается только
явной просьбой. Этот скил сохраняет hotel-инструменты для составных сценариев.

Все вертикали этого скилла — **только поиск**. Ни одна не доводит до оплаты:

- **Поезда** (`train_search`) — оплата уходит в браузерную форму, которой у MCP нет.
- **Самолёты** (`flight_search`) — брони и оплаты в тулах нет вовсе.
- **Отели** (`hotel_search`) — доступны поиск, тарифы, отзывы и карточка, брони
  и оплаты нет.
- **Маркетплейс** (`shop_search`/`shop_cart`) — размещения заказа нет, только поиск
  и расчёт доставки.

Во всех четырёх случаях — покажи пользователю варианты и скажи прямо: «оформить
через MCP нельзя, дальше — в приложении».

## Инструменты

| Тул | Что делает | Деньги |
|---|---|---|
| `train_stations(search_text, limit)` | Название города/станции → числовой `searchCode` для поиска | нет |
| `train_search(origin, destination, date, adults, children, limit)` | Поиск поездов. `origin`/`destination` — ЧИСЛОВЫЕ коды станций | нет |
| `compare_train_prices(origin, destination, dates, ...)` | Сравнить поезда для нескольких дат и получить готовые дельты | нет |
| `flight_search(from_code, to_code, date, adults, children, infants, only_bookable, limit)` | Поиск авиабилетов. `from_code`/`to_code` — коды IATA | нет |
| `compare_flight_prices(from_code, to_code, dates, ...)` | Сравнить авиабилеты для нескольких дат с фильтрами и дельтами | нет |
| `flight_history()` | История авиапоисков — единственный источник кодов IATA с названиями городов | нет |
| `flight_price_calendar(from_code, to_code, departure_from, departure_to, from_kind, to_kind, ...)` | Календарь минимальных цен по датам вылета (кэш банка, не живой поиск) | нет |
| `flight_price_forecast(search_id)` | Вырастет ли цена по уже выполненному `flight_search` до вылета | нет |
| `flight_schedule(from_code, to_code, date, limit)` | Расписание рейсов направления (какие рейсы вообще летают и по каким дням), не живой поиск цен | нет |
| `geodata_by_code(codes, limit)` | Имена и координаты города/аэропорта по коду IATA — единственный публичный «код → название» | нет |
| `audience_profile()` | Безопасная возрастная группа и допустимость 18+ для фильтрации афиши, без даты рождения и пола | нет |
| `hotel_autocomplete(query, limit)` | Локации и отели с id для следующего шага | нет |
| `hotel_search(destination_id, checkin_date, checkout_date, adults, children_ages, limit)` | Доступные отели и цены | нет |
| `hotel_search_filters(location_id, checkin_date, checkout_date, adults, children_ages, filters, ...)` | Доступные значения фильтров и число подходящих отелей для конкретного поиска | нет |
| `hotel_latest_offers(hotel_ids, checkin_date, checkout_date, location_id, adults, children_ages, filters)` | Массово перепроверить цены и условия финального shortlist перед сравнением | нет |
| `compare_hotel_prices(destination_id, windows, ...)` | Сравнить полную цену/цену за ночь для нескольких окон | нет |
| `compare_flight_hotel_prices(from_code, to_code, hotel_destination_id, windows, ...)` | Сложить два перелёта и отель для нескольких окон | нет |
| `hotel_details(hotel_id, max_facilities, max_images)` | Адрес, описание, заезд/выезд, удобства и официальные фото | нет |
| `hotel_rates(hotel_id, checkin_date, checkout_date, adults, children_ages, filters, limit)` | Комнаты и живые тарифы выбранного отеля | нет |
| `hotel_checkout_url(hotel_id, checkin_date, checkout_date, book_hash, guests, rate_confirmed)` | Ссылка на оформление явно выбранного тарифа | нет |
| `hotel_reviews(hotel_id, source_code, sort, sort_type, cursor, page_size, search_text)` | Отзывы, фото, лайки и cursor-пагинация | нет |
| `hotel_filters(max_chars)` | Текущая структура фильтров поиска | нет |
| `nearby_search(city, anchor_name, address, latitude, longitude, include_poi, place_kinds, limit)` | Рестораны и POI OpenStreetMap в радиусе 1,8 км | нет |
| `weather(city, latitude, longitude, date_from, date_to)` | Прогноз Open-Meteo или климат ERA5 | нет |
| `shop_search(query, limit, offset)` | Поиск товаров в маркетплейсе Т-Банка (Город → Шопинг) | нет |
| `shop_cart(limit)` | Корзины маркетплейса — по одной на продавца, read-only | нет |

## Поезда

1. Вызови `train_stations(search_text)` отдельно для отправления и назначения.
   Возьми числовой `searchCode`; если пользователь назвал город, предпочитай
   результат `type=City`, а не конкретный вокзал.
2. `train_search(origin, destination, date)` → список поездов с ценой (по
   вагону минимальная) и числом мест. `date` — YYYY-MM-DD.
3. Скажи пользователю: «Оформить и оплатить билет через MCP нельзя — оплата
   уходит в веб-форму банка. Дальше — в приложении.»

## Самолёты

`flight_search`, `flight_price_calendar`, `flight_price_forecast`,
`flight_schedule` и `geodata_by_code` — публичные (подтверждено на проде:
ни Bearer, ни sessionid не уходят), в отличие от `flight_history`,
который читает историю поисков ЭТОЙ сессии и без входа не работает.
Так что `flight_search` и `geodata_by_code` доступны даже без
предварительного `login()`.

1. Резолвера «город → код IATA» нет, но обратное направление «код →
   название, координаты, timezone» есть — это `geodata_by_code(codes)`. Если
   пользователь называет город словами и нужны только названия/координаты,
   возьми код из `flight_history()` (там коды приходят вместе с названиями)
   или попроси пользователя назвать его сам. Не подставляй по памяти.
2. Если пользователь не назвал конкретную дату («когда дешевле слетать»),
   сначала вызови `flight_price_calendar(from_code, to_code)` — это чтение
   кэша банка, а не поиск, поэтому быстрее и не требует одной точной даты;
   пустой ответ значит «даты нет в кэше», а не «рейсов нет». Если нужно узнать
   не цену, а КАКИЕ рейсы вообще летают по направлению и по каким дням —
   `flight_schedule(from_code, to_code)`.
3. `flight_search(from_code, to_code, date)` → предложения, отсортированные
   по цене. `only_bookable=True` (по умолчанию) — только то, что банк в
   принципе продаёт сам; `False` — весь поток партнёров, дольше и почти
   бесполезно (уводит на чужой сайт).
4. Если пользователь спрашивает, стоит ли покупать сейчас или подождать,
   возьми `searchId` из `flight_search(..., response_format="json")` и
   передай его в `flight_price_forecast(search_id)`.
5. Скажи пользователю: «Купить билет через MCP нельзя — здесь только поиск и
   сравнение. Бронирование и оплата — в приложении.»

## Отели

1. `hotel_autocomplete(query)` → возьми id локации. Запрос требует минимум три
   символа; id по названию не угадывай.
2. `hotel_search(destination_id, checkin_date, checkout_date, limit=100)` → отели
   и цены. **Всегда явно передавай `limit=100` и получай не менее 100 отелей, если
   столько доступно.** Не уменьшай лимит ради короткого ответа. **Как только
   накоплено хотя бы 5 карточек, сразу покажи первую порцию из 5 отелей — не жди
   `isLoadingCompleted=true`, `meta.complete=true` или загрузки всех 100.** Если
   поиск ещё идёт, прямо пометь результат как неполный и укажи, сколько карточек
   уже получено; не выдавай `total` за число загруженных вариантов. После первой
   порции продолжай дозагрузку полного пула для следующих запросов `Показать ещё`,
   фильтрации и сравнения. Сохрани все полученные карточки (стремись накопить
   минимум 100 при наличии), не заменяя полный пул шорт-листом и не теряя
   `hotelId`, `imageUrl`, цену, рейтинг, адрес и координаты. Если поиск завершён и
   всего доступно меньше 100, сохрани все и прямо назови фактическое число.
   Даты — YYYY-MM-DD; возраста детей — строка `5,12` или JSON `[5,12]`.
3. Если пользователь задаёт критерии или спрашивает, сколько вариантов им
   соответствует, вызови `hotel_search_filters(..., response_format="json")` с
   теми же локацией, датами и гостями. Передавай выбранные значения как
   `{"filterId":"stars","value":["4","5"]}`; range — строки `min=...` /
   `max=...`, boolean — `true`/`false`. Это availability-aware метод.
   `hotel_filters()` — общий каталог для UI и фильтров `hotel_rates()`, он не
   показывает доступность для конкретных дат и гостей.
4. Для финального shortlist перед сравнением одним вызовом
   `hotel_latest_offers(hotel_ids, ...)` перепроверь текущую цену, наличие,
   питание, оплату и отмену. Если `price.isFinalPrice=false`, не делай выводов
   об остальных условиях: по контракту они не подтверждены. Отсутствующий
   `hotel_id` означает, что актуальное предложение для него не вернулось.
5. Перед любым выводом информации об отеле в чат обязательно вызови
   `hotel_details(hotel_id)` для каждого показываемого отеля. Карточка в ответе
   должна содержать как минимум название, звёзды, рейтинг, актуальную цену с
   датами и составом гостей, адрес, описание, время заезда/выезда и основные
   удобства. Перед показом фотографии скачай `imageUrl` из сохранённой карточки
   `hotel_search()` через `curl` в доступный для записи локальный каталог. Добавь
   фотографию отдельной Markdown-строкой `![Название отеля](/absolute/path.jpg)`,
   используя абсолютный путь к скачанному локальному файлу; удалённый `imageUrl`
   напрямую в чат не вставляй. Никогда не выводи отель только названием и ценой и
   не подменяй фотографию текстовой ссылкой. Если у карточки нет `imageUrl` или
   файл скачать не удалось, прямо скажи, что фотография недоступна, и не
   придумывай URL. В конце деталей каждого
   отеля обязательно добавь отдельной строкой ссылку, построенную из точного
   `hotelId`: `[https://www.tbank.ru/travel/hotels/new/hotels/{hotelId}](https://www.tbank.ru/travel/hotels/new/hotels/{hotelId})`.
6. Для выбранного варианта после `hotel_details(hotel_id)` вызови
   `hotel_rates(hotel_id, checkin_date, checkout_date, ...)`: цена из общей
   выдачи — предварительная, а этот вызов даёт конкретные комнаты, питание,
   оплату и правила отмены. Для допустимой структуры rate-фильтров сначала вызови
   `hotel_filters()` и передай выбранные объекты в `filters`.
7. Если пользователь спрашивает об опыте гостей, вызови `hotel_reviews(hotel_id)`.
   Следующую страницу получай только с cursor из предыдущего ответа. Для отзывов
   с фото передай `search_text="onlyPhotos"`.
8. Если пользователь хочет перейти к оформлению, сначала покажи тарифы и уточни,
   какой именно он выбирает. Только после явного выбора вызови
   `hotel_checkout_url(...)` с `book_hash` выбранного тарифа из `hotel_rates()` и
   `rate_confirmed=true`. Ссылка ничего не бронирует и не оплачивает; итоговые
   цену и условия пользователь проверяет на странице T-Bank.

### Выдача большого списка в чате

Полный пул и видимая выдача — разные сущности. Начинай видимую выдачу сразу после
получения первых 5 карточек; полный пул дозагружай отдельно и не публикуй одним
сообщением:

1. В первой порции покажи 5 отелей сразу, как только они получены. По прямой
   просьбе пользователя можно показать до 10, но не задерживай первые 5 ради
   ожидания остальных. В начале ответа укажи число уже полученных вариантов,
   даты, гостей, активные фильтры и сортировку; если поиск завершён, дополнительно
   можно назвать итоговое число.
2. Присвой отелям короткие стабильные метки `H1`, `H2`, ... в текущей задаче.
   Метка не меняется после дозагрузки, фильтрации или сортировки и всегда связана
   с исходным `hotelId`. Не используй позицию карточки как единственный
   идентификатор.
3. Карточки располагай вертикально. После обязательной фотографии покажи название,
   звёзды и рейтинг, цену за ночь и за все даты, адрес или расстояние до ориентира,
   2–4 важных удобства и краткое описание. Не дублируй длинный текст из
   `hotel_details()`; оставь достаточно данных для выбора. Заверши карточку
   обязательной ссылкой на просмотр отеля по шаблону
   `https://www.tbank.ru/travel/hotels/new/hotels/{hotelId}`.
4. В конце каждой карточки напиши доступные команды обычным текстом:
   `Подробнее H1`, `Отзывы H1`, `Сравнить H1`. Не имитируй несуществующие
   кликабельные кнопки. В конце порции предложи `Показать ещё` и покажи прогресс,
   например «Показано 5 из 126».
5. На `Показать ещё` выведи следующую порцию ранее не показанных отелей в той же
   сортировке. Не повторяй уже показанные карточки. Новые фильтры начинают видимую
   выдачу заново по отфильтрованному полному пулу, но не удаляют выбранные для
   сравнения отели без предупреждения.
6. Если результат неполный, отделяй «получено» от заявленного `total`: не пиши
   «найдено 126», когда загружено только 5. Сообщи, какая часть выдачи доступна,
   покажи первые 5 без ожидания завершения и продолжи загрузку согласно шагу 2
   раздела «Отели».

### Выбор и сравнение отелей

1. Веди shortlist отдельно от полного пула и видимой страницы. Пользователь может
   добавлять варианты командами `Сравнить H1`, `Добавь H1 и H3` или по названию.
   После каждого изменения коротко покажи состав shortlist и команды
   `Сравнить выбранные`, `Убрать H1`, `Очистить сравнение`.
2. Для отдельной подборки целевой shortlist — 5 отелей, для полной поездки —
   ровно 3. Выбор сохраняй при дозагрузке, смене сортировки, фильтров и просмотре
   отзывов.
3. Перед итоговым сравнением обогати каждый вариант по каноническому flow из
   `travel-output-modes`: массовый `hotel_latest_offers()`, затем актуальные
   `hotel_details(max_images=3)`, `hotel_rates()` и одна сопоставимая страница
   `hotel_reviews()` на отель. Уже полученный в этой задаче ответ с теми же
   параметрами можно переиспользовать; устаревшие или неполные сведения не
   считай подтверждёнными.
4. Загрузи для каждого сравниваемого отеля по одной сопоставимой странице отзывов:
   используй одинаковые `sort`, `sort_type` и `page_size`. Если отзывы по отелю уже
   накоплены в текущей задаче, сохрани их и при необходимости дозагрузи следующую
   страницу только с ранее полученным `cursor`; не заменяй и не дублируй выборку.
   По всей накопленной выборке каждого отеля составь отдельный краткий обзор:
   повторяющиеся плюсы, повторяющиеся минусы и вывод «для кого подходит».
5. Итог всегда выводи одной сравнительной Markdown-таблицей: отели — столбцы,
   критерии — строки. Обязательные строки: полная цена, цена за ночь, рейтинг и
   число отзывов, расположение, тип номера, питание, отмена, способ и момент
   оплаты, основные удобства, `Плюсы по отзывам`, `Минусы по отзывам`,
   `Для кого подходит`. В строках обзора не смешивай отзывы разных отелей и
   укажи размер реально загруженной выборки; длинные пункты разделяй через `<br>`.
   Общие параметры можно сократить, но обязательные строки не убирай.
6. Явно отмечай лучший вариант по каждому объективному критерию, но не объявляй
   один отель победителем без заданных пользователем приоритетов. Если приоритеты
   известны, дай рекомендацию и кратко объясни компромисс.
7. Если сохранённая цена была предварительной, так и пометь её. Не представляй
   сохранённые питание, оплату или отмену как заново подтверждённые условия и
   укажи время проверки, если оно есть в загруженных данных.

### Отзывы и обзор отзывов

1. По команде `Отзывы H1` сначала загрузи одну страницу через `hotel_reviews()` и
   покажи обзор перед отдельными отзывами. Обзор должен содержать повторяющиеся
   сильные стороны, повторяющиеся замечания и важный компромисс для выбора.
2. Всегда подпиши базу обзора: «по N загруженным отзывам», применённую сортировку
   и доступный диапазон дат. Не выдавай выборку за все отзывы отеля и не называй
   доли или проценты, если источник их не вернул и они не рассчитаны над явно
   указанной загруженной выборкой.
3. После обзора покажи 3–5 репрезентативных отзывов: оценку, дату, автора, если он
   доступен, короткий фрагмент и наличие фото. Сохраняй баланс положительных и
   критических отзывов; не выбирай только подтверждающие итоговый вывод.
4. Команда `Показать ещё отзывы H1` вызывает следующую страницу только с `cursor`
   предыдущего ответа. Добавляй новые отзывы к уже загруженным, не заменяй старые,
   не повторяй дубликаты и показывай прогресс «загружено N из total», если `total`
   доступен. Если cursor отсутствует, сообщи, что отзывы закончились.
5. После каждой дозагрузки пересобери обзор по всей накопленной выборке и укажи
   новый размер выборки. Если новые отзывы меняют прежний вывод, скажи об этом
   прямо. Не смешивай отзывы разных отелей в один обзор.
6. При сравнении отзывов нескольких отелей используй сопоставимые выборки и одну
   сортировку, насколько позволяет источник. Для каждого отеля сформируй поля
   `Плюсы по отзывам`, `Минусы по отзывам` и `Для кого подходит` и вынеси их в
   общую сравнительную таблицу. Больший `reviewCount` сам по себе не означает
   более высокое качество.

Hotel-вызовы идут в публичный `hotels.tbank.ru` без банковского access token и
sessionid. Если в SSO-сессии доступен `ssoId`, передаётся только этот cookie.

## Сравнение дат и цен

1. Если пользователь дал несколько дат или просит «а если сдвинуть поездку»,
   предпочитай соответствующий `compare_*`, а не вызывай атомарный поиск по
   одному разу и не считай разницу в модели.
2. Первая дата/окно — baseline. Поля `deltaRubFromBaseline` и
   `deltaPctFromBaseline` уже содержат подписанную разницу. Отрицательное значение
   означает экономию относительно baseline.
3. `lowest observed` — минимум только среди полученных данных. Если
   `meta.complete=false`, обязательно сохрани предупреждение о неполной выдаче.
4. `compare_flight_hotel_prices()` считает только перелёт туда, перелёт обратно и
   отель. Не называй `bundleTotalRub` полной стоимостью поездки и не добавляй к
   ней расходы, которых нет в результате.

## Места рядом и погода

1. Возьми координаты выбранного отеля из `hotel_search()` или `hotel_details()`.
   Если координат нет, `nearby_search(city, address=...)` сам резолвит адрес через
   Nominatim. Рестораны возвращаются всегда; для достопримечательностей передай
   `include_poi=True` и нужные `place_kinds`: `culture`, `nature`, `nightlife`.
2. Вызови `weather(city, latitude, longitude, date_from, date_to)`. Поле `kind`
   обязательно интерпретируй буквально: `forecast` — прогноз ближайших 16 дней,
   `climate` — статистическая оценка по ERA5 за 1991–2020, не прогноз.
3. Оба источника публичные, без API-ключей и без банковских token/cookie. При
   `warnings` покажи пользователю, какая часть результата отсутствует.

Все перечисленные инструменты, включая маркетплейс, находятся в едином
`tbank-mcp`. Для резолва ЖД-кодов используй `train_stations`; `train_calendar`
показывает календарь продаж и не заменяет резолвер станций.

## Маркетплейс (Город → Шопинг)

1. `shop_search(query)` → товары с ценой, продавцом, рейтингом, `skuId`/
   `pointId`/`shopId` (они опознают позицию, но добавить её в корзину через
   MCP нельзя — тула для этого нет).
2. `shop_cart()` — что уже лежит в корзинах (по одной на продавца), read-only.
3. Скажи пользователю: «Оформить заказ через MCP нельзя — ни добавление в
   корзину, ни оплата не реализованы. Собранную корзину нужно оформлять в
   приложении.»

## Ключевые правила

1. **Ни одна из четырёх вертикалей не доходит до оплаты через MCP.** Не
   обещай пользователю бронирование или покупку — сразу говори, что дальше
   нужно приложение.
2. **Коды (станций, IATA) не выдумывай.** Бери их из `train_stations()` /
   `flight_history()`, а не по памяти — банк не резолвит названия городов сам.
3. **`only_bookable=True` для `flight_search`** — если не попросили иначе:
   без него поиск идёт секундами дольше и в основном отдаёт партнёрские
   предложения, которые всё равно не купить через MCP.
4. **Не считай цены и проценты сам, если подходит `compare_*`.** Бери готовые
   дельты из структурированного ответа и сохраняй его оговорки о полноте.
5. **Показывай первые 5 отелей сразу, не дожидаясь полного поиска.** Затем
   дозагружай полный пул до 100 карточек, если они доступны. Любой показанный в
   чате отель сначала обогащай через `hotel_details()`, скачивай фотографию из
   `hotel_search().imageUrl` через `curl`, показывай локальный файл по абсолютному
   пути и добавляй обязательную ссылку
   `https://www.tbank.ru/travel/hotels/new/hotels/{hotelId}`.
6. **Большой пул показывай порциями, а shortlist храни отдельно.** По умолчанию
   выводи 5 отелей со стабильными метками и сохраняй выбор при пагинации.
7. **Обзор отзывов ограничивай реально загруженной выборкой.** Дозагружай только
   по cursor, накапливай страницы и пересобирай обзор с явным размером выборки.
8. **Перед сравнением актуализируй финальный shortlist.** Используй массовый
   `hotel_latest_offers()`, детали, тарифы и сопоставимую страницу отзывов по
   правилам `travel-output-modes`; не повторяй вызов, если в текущей задаче уже
   есть свежий ответ с теми же параметрами.
9. **Для финальной поездки обогати все три отеля одинаково.** Используй
   `hotel_details(max_images=3)`, актуальные тарифы и по 10 последних отзывов;
   собери общий HTML-блок и таблицу по правилам `travel-output-modes`.
