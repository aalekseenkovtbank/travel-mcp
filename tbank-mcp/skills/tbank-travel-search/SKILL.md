# Поиск: поезда, погода и составная поездка

Для полной поездки используй `tbank-trip-generation`; итоговый digest возвращает
`get_trip_report(output_mode="html"|"markdown")`.
Все инструменты этого skill read-only: ссылки checkout только передают управление
пользователю, а оформление выполняется вне MCP.

## Активные инструменты

Поверхность содержит 33 инструмента: поиск/сравнение авиа и ЖД, поиск и тарифы
отелей, погоду, агрегированную персонализацию, сборку и рендер страниц, а также
инструкции. Точные имена, сигнатуры и лимиты определяются `tools/list` и
их короткими MCP descriptions; не вызывай инструмент, которого нет в allowlist.

## Поезда

1. Вызови `train_stations(search_text)` отдельно для отправления и назначения.
   Возьми числовой `searchCode`; если пользователь назвал город, предпочитай
   результат `type=City`, а не конкретный вокзал.
2. `train_search(origin, destination, date)` → список поездов с ценой (по
   вагону минимальная) и числом мест. `date` — YYYY-MM-DD.
3. Скажи пользователю: «Оформить и оплатить билет через MCP нельзя — оплата
   уходит в веб-форму банка. Дальше — в приложении.»

## Авиа

Для standalone поиска авиабилетов, сравнений дат, прямых альтернатив и
авиа-ссылок используй отдельный skill `tbank-flight-search`. В составной поездке
следуй его авиа-алгоритму, а страницу собирай по `trip-generation`.

## Отели

1. `hotel_autocomplete(query)` → возьми id локации. Запрос требует минимум три
   символа; id по названию не угадывай.
2. `hotel_search(destination_id, checkin_date, checkout_date)` → до 50 отелей
   с дожданной выдачей и обновлёнными офферами. Не передавай `limit` больше 50.
   `total` — размер каталога, не длина `hotels`. Если `meta.complete=false` или
   `isFinalPrice=false`, не обещай цену и условия. Для «показать ещё» сужай
   фильтрами, а не увеличивай лимит выше капа. Сохрани полученные карточки,
   не заменяя пул шорт-листом и не теряя
   `hotelId`, `imageUrl`, цену, рейтинг, адрес и координаты. Если поиск завершён и
   всего доступно меньше 100, сохрани все и прямо назови фактическое число.
   Даты — YYYY-MM-DD; возраста детей — строка `5,12` или JSON `[5,12]`.
3. Если пользователь задаёт критерии или спрашивает, сколько вариантов им
   соответствует, вызови `hotel_search_filters(..., response_format="json")` с
   теми же локацией, датами и гостями. Передавай выбранные значения как
   `{"filterId":"stars","value":["4","5"]}`; range — строки `min=...` /
   `max=...`, boolean — `true`/`false`. Это availability-aware метод.
   `hotel_filters()` — общий каталог для UI и фильтров `hotel_rates()`, он не
   показывает доступность для конкретных дат и гостей.
4. Для финального shortlist перед сравнением одним вызовом
   `hotel_latest_offers(hotel_ids, ...)` перепроверь текущую цену, наличие,
   питание, оплату и отмену. Если `price.isFinalPrice=false`, не делай выводов
   об остальных условиях: по контракту они не подтверждены. Отсутствующий
   `hotel_id` означает, что актуальное предложение для него не вернулось.
5. Перед любым выводом информации об отеле в чат обязательно вызови
   `hotel_details(hotel_id)` для каждого показываемого отеля. Карточка в ответе
   должна содержать как минимум название, звёзды, рейтинг, актуальную цену с
   датами и составом гостей, адрес, описание, время заезда/выезда и основные
   удобства. Перед показом фотографии: если хост может показывать локальные
   файлы (локальный агент), скачай `imageUrl` из сохранённой карточки
   `hotel_search()` через `curl` в доступный для записи локальный каталог и
   добавь Markdown-строкой `![Название отеля](/absolute/path.jpg)`; если хост
   удалённый и локальные файлы ему не видны (например ChatGPT), вставляй сам
   HTTPS `imageUrl`. Никогда не выводи отель только названием и ценой и
   не подменяй фотографию текстовой ссылкой. Если у карточки нет `imageUrl` или
   файл скачать не удалось, прямо скажи, что фотография недоступна, и не
   придумывай URL. В конце деталей каждого
   отеля обязательно добавь отдельной строкой ссылку, построенную из точного
   `hotelId`: `[Открыть отель в T-Bank](https://www.tbank.ru/travel/hotels/new/hotels/{hotelId})`.
   Для фиктивного или невалидного id напиши «Ссылка T-Bank недоступна» и не
   подставляй общий раздел отелей.
6. Для выбранного варианта после `hotel_details(hotel_id)` вызови
   `hotel_rates(hotel_id, checkin_date, checkout_date, ...)`: цена из общей
   выдачи — предварительная, а этот вызов даёт конкретные комнаты, питание,
   оплату и правила отмены. Для допустимой структуры rate-фильтров сначала вызови
   `hotel_filters()` и передай выбранные объекты в `filters`.
7. Если пользователь спрашивает об опыте гостей, вызови `hotel_reviews(hotel_id)`.
   Следующую страницу получай только с cursor из предыдущего ответа. Для отзывов
   с фото передай `search_text="onlyPhotos"`.
8. Если пользователь хочет перейти к оформлению, сначала покажи тарифы и уточни,
   какой именно он выбирает. Только после явного выбора вызови
   `hotel_checkout_url(...)` с `book_hash` выбранного тарифа из `hotel_rates()` и
   `rate_confirmed=true`. Ссылка ничего не бронирует и не оплачивает; итоговые
   цену и условия пользователь проверяет на странице T-Bank.

### Выдача большого списка в чате

Полный пул и видимая выдача — разные сущности. Начинай видимую выдачу сразу после
получения первых 5 карточек; полный пул дозагружай отдельно и не публикуй одним
сообщением:

1. В первой порции покажи 5 отелей сразу, как только они получены. По прямой
   просьбе пользователя можно показать до 10, но не задерживай первые 5 ради
   ожидания остальных. В начале ответа укажи число уже полученных вариантов,
   даты, гостей, активные фильтры и сортировку; если поиск завершён, дополнительно
   можно назвать итоговое число.
2. Присвой отелям короткие стабильные метки `H1`, `H2`, ... в текущей задаче.
   Метка не меняется после дозагрузки, фильтрации или сортировки и всегда связана
   с исходным `hotelId`. Не используй позицию карточки как единственный
   идентификатор.
3. Карточки располагай вертикально. После обязательной фотографии покажи название,
   звёзды и рейтинг, цену за ночь и за все даты, адрес или расстояние до ориентира,
   2–4 важных удобства и краткое описание. Не дублируй длинный текст из
   `hotel_details()`; оставь достаточно данных для выбора. Заверши карточку
   обязательной ссылкой на просмотр отеля по шаблону
   `https://www.tbank.ru/travel/hotels/new/hotels/{hotelId}`.
4. В конце каждой карточки напиши доступные команды обычным текстом:
   `Подробнее H1`, `Отзывы H1`, `Сравнить H1`. Не имитируй несуществующие
   кликабельные кнопки. В конце порции предложи `Показать ещё` и покажи прогресс,
   например «Показано 5 из 126».
5. На `Показать ещё` выведи следующую порцию ранее не показанных отелей в той же
   сортировке. Не повторяй уже показанные карточки. Новые фильтры начинают видимую
   выдачу заново по отфильтрованному полному пулу, но не удаляют выбранные для
   сравнения отели без предупреждения.
6. Если результат неполный, отделяй «получено» от заявленного `total`: не пиши
   «найдено 126», когда загружено только 5. Сообщи, какая часть выдачи доступна,
   покажи первые 5 без ожидания завершения и продолжи загрузку согласно шагу 2
   раздела «Отели».

### Выбор и сравнение отелей

1. Веди shortlist отдельно от полного пула и видимой страницы. Пользователь может
   добавлять варианты командами `Сравнить H1`, `Добавь H1 и H3` или по названию.
   После каждого изменения коротко покажи состав shortlist и команды
   `Сравнить выбранные`, `Убрать H1`, `Очистить сравнение`.
2. Для отдельной подборки целевой shortlist — 5 отелей, для полной поездки —
   ровно 3. Выбор сохраняй при дозагрузке, смене сортировки, фильтров и просмотре
   отзывов.
3. Перед итоговым сравнением обогати каждый вариант по каноническому flow из
   правила отельного flow: массовый `hotel_latest_offers()`, затем актуальные
   `hotel_details(max_images=3)`, `hotel_rates()` и одна сопоставимая страница
   `hotel_reviews()` на отель. Уже полученный в этой задаче ответ с теми же
   параметрами можно переиспользовать; устаревшие или неполные сведения не
   считай подтверждёнными.
4. Загрузи для каждого сравниваемого отеля по одной сопоставимой странице отзывов:
   используй одинаковые `sort`, `sort_type` и `page_size`. Если отзывы по отелю уже
   накоплены в текущей задаче, сохрани их и при необходимости дозагрузи следующую
   страницу только с ранее полученным `cursor`; не заменяй и не дублируй выборку.
   По всей накопленной выборке каждого отеля составь отдельный краткий обзор:
   повторяющиеся плюсы, повторяющиеся минусы и вывод «для кого подходит».
5. Итог всегда выводи одной сравнительной Markdown-таблицей: отели — столбцы,
   критерии — строки. Обязательные строки: полная цена, цена за ночь, рейтинг и
   число отзывов, расположение, тип номера, питание, отмена, способ и момент
   оплаты, основные удобства, `Плюсы по отзывам`, `Минусы по отзывам`,
   `Для кого подходит`. В строках обзора не смешивай отзывы разных отелей и
   укажи размер реально загруженной выборки; длинные пункты разделяй через `<br>`.
   Общие параметры можно сократить, но обязательные строки не убирай.
6. Явно отмечай лучший вариант по каждому объективному критерию, но не объявляй
   один отель победителем без заданных пользователем приоритетов. Если приоритеты
   известны, дай рекомендацию и кратко объясни компромисс.
7. Если сохранённая цена была предварительной, так и пометь её. Не представляй
   сохранённые питание, оплату или отмену как заново подтверждённые условия и
   укажи время проверки, если оно есть в загруженных данных.

### Отзывы и обзор отзывов

1. По команде `Отзывы H1` сначала загрузи одну страницу через `hotel_reviews()` и
   покажи обзор перед отдельными отзывами. Обзор должен содержать повторяющиеся
   сильные стороны, повторяющиеся замечания и важный компромисс для выбора.
2. Всегда подпиши базу обзора: «по N загруженным отзывам», применённую сортировку
   и доступный диапазон дат. Не выдавай выборку за все отзывы отеля и не называй
   доли или проценты, если источник их не вернул и они не рассчитаны над явно
   указанной загруженной выборкой.
3. После обзора покажи 3–5 репрезентативных отзывов: оценку, дату, автора, если он
   доступен, короткий фрагмент и наличие фото. Сохраняй баланс положительных и
   критических отзывов; не выбирай только подтверждающие итоговый вывод.
4. Команда `Показать ещё отзывы H1` вызывает следующую страницу только с `cursor`
   предыдущего ответа. Добавляй новые отзывы к уже загруженным, не заменяй старые,
   не повторяй дубликаты и показывай прогресс «загружено N из total», если `total`
   доступен. Если cursor отсутствует, сообщи, что отзывы закончились.
5. После каждой дозагрузки пересобери обзор по всей накопленной выборке и укажи
   новый размер выборки. Если новые отзывы меняют прежний вывод, скажи об этом
   прямо. Не смешивай отзывы разных отелей в один обзор.
6. При сравнении отзывов нескольких отелей используй сопоставимые выборки и одну
   сортировку, насколько позволяет источник. Для каждого отеля сформируй поля
   `Плюсы по отзывам`, `Минусы по отзывам` и `Для кого подходит` и вынеси их в
   общую сравнительную таблицу. Больший `reviewCount` сам по себе не означает
   более высокое качество.

Hotel-вызовы идут в публичный `hotels.tbank.ru` без банковского access token и
sessionid. Если в SSO-сессии доступен `ssoId`, передаётся только этот cookie.

## Сравнение дат и цен

1. Если пользователь дал несколько дат или просит «а если сдвинуть поездку»,
   предпочитай соответствующий `compare_*`, а не вызывай атомарный поиск по
   одному разу и не считай разницу в модели.
2. Первая дата/окно — baseline. Поля `deltaRubFromBaseline` и
   `deltaPctFromBaseline` уже содержат подписанную разницу. Отрицательное значение
   означает экономию относительно baseline.
3. `lowest observed` — минимум только среди полученных данных. Если
   `meta.complete=false`, обязательно сохрани предупреждение о неполной выдаче.
4. `compare_flight_hotel_prices()` считает только перелёт туда, перелёт обратно и
   отель. Не называй `bundleTotalRub` полной стоимостью поездки и не добавляй к
   ней расходы, которых нет в результате.

## Погода

Вызови `weather(city, latitude, longitude, date_from, date_to)` для диапазона
до 30 дней. Поле `kind` интерпретируй буквально: `forecast` — ближайшие 16 дней,
`climate` — статистическая оценка ERA5 за 1991–2020. При `warnings` покажи,
какая часть результата отсутствует.

Для ЖД-кодов используй `train_stations`; не подставляй коды по памяти.

## Ключевые правила

1. **Не выдумывай коды, цены, расписания, наличие, фото и URL.** Используй
   `search_iata_code()`/`geodata_by_code()` и `train_stations()` как резолверы.
2. **`only_bookable=True` для `flight_search`** — значение по умолчанию для
   предложений, которые можно продолжить в T-Bank.
3. **Используй `compare_*`, когда нужен сдвиг дат.** Бери дельты и warnings из
   структурированного результата; lowest observed относится только к полученным
   данным.
4. **Перед сравнением отелей вызови `hotel_latest_offers()`.** При нефинальной
   цене не подтверждай условия; финальный тариф и bookHash бери из
   `hotel_rates()`.
5. Для составной поездки передай найденные транспорт и отели в
   `tbank-trip-generation` и вызови `get_trip_report()`; файлы не пишутся.
