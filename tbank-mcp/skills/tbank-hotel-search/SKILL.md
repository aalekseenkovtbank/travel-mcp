# Поиск отелей с фотографиями

Результат — компактный шорт-лист реальных доступных вариантов прямо в чате.
Поиск только читает данные: он не бронирует номер и не списывает деньги.

## Сессия и приватность

В начале вызови `session_status()`. Успешный вызов подхватывает сохранённую
локальную сессию `tbank-mcp`, узнаёт и сохраняет `ssoId`, если он доступен.
Отельные методы не получают банковский access token, `sessionid`, логин или
пароль: в Hotels API может передаваться только `ssoId`. Поэтому называй выдачу
полученной в контексте сохранённой SSO-сессии, но не обещай персональную цену,
если источник сам её не обозначил.

Если сессия истекла, попроси пользователя войти через локальную команду login и
остановись. Не проси телефон, SMS-код, пароль или PIN в чате. Не показывай в
ответе содержимое сессии, cookie или банковские данные.

## Значения по умолчанию

Явно указанные пользователем параметры всегда имеют приоритет. Остальные
нормализуй без лишнего уточнения:

- Если состав гостей не указан, ищи для двух взрослых: `adults=2`, детей нет.
  Не переноси этот дефолт на явно упомянутых детей: если ребёнок указан без
  возраста, задай один короткий вопрос о возрасте.
- Если город отправления не указан, вызови
  `orders(kind="путешествия", response_format="json")` и определи основной
  город по недавним завершённым транспортным заказам. Учитывай только заказы, в
  которых пункт отправления указан явно; выбери самый частый город, при равенстве
  — самый свежий. Не считай последний поиск авиабилетов текущим местоположением
  и не читай для этого отдельные операции. Если пригодной или однозначной
  истории нет, спроси город отправления. Для hotel API город отправления не
  является параметром, но сохрани его в нормализованном запросе и покажи среди
  принятых допущений.
- Если даты не указаны, возьми ближайшее будущее окно с вечера пятницы по вечер
  воскресенья. В hotel-инструменты передай календарные даты: заезд в пятницу,
  выезд в воскресенье; время они не принимают.
- Если пользователь указал не точные даты, а допустимый диапазон, возьми первое
  будущее окно пятница–воскресенье, которое целиком находится внутри диапазона.
  Если полного такого окна нет, не выходи за границы диапазона и задай один
  короткий вопрос о датах.

В первой строке результата явно перечисли применённые допущения: город
отправления из истории заказов, два взрослых и/или выбранное окно выходных.

## Поиск

1. Из запроса и правил по умолчанию определи город или объект назначения, город
   отправления, даты заезда и выезда, число взрослых и возраста детей, а также
   бюджет и пожелания. Вопрос задавай только для данных, которые нельзя получить
   из запроса, дефолтов или пригодной истории travel-заказов.
2. Вызови `hotel_autocomplete(query, response_format="json")` и используй id
   подходящей локации. Если есть несколько одноимённых мест, дай пользователю
   выбрать; id по названию не придумывай.
3. Вызови `hotel_search(..., response_format="json")` с теми же датами и гостями.
   Обычно загрузи 30–50 карточек, чтобы из них получился содержательный шорт-лист.
4. Отбери 5–8 вариантов по явным критериям пользователя. Для звёздности, цены,
   рейтинга и расположения используй поля карточек. Если запрос зависит от
   доступных фильтров, сначала вызови `hotel_search_filters()` с теми же датами и
   гостями. Этот метод показывает доступность и число совпадений, но не заменяет
   `hotel_search()`.
5. Перед показом цен и условий вызови одним запросом
   `hotel_latest_offers(hotel_ids, ..., response_format="json")` для всего
   шорт-листа. Сопоставляй ответы по `hotelId`, сохраняя название, адрес и
   `imageUrl` из исходной выдачи. Не показывай как доступный отель, для которого
   актуальное предложение не вернулось.
6. Если важны удобства, конкретный тип номера, питание, оплата или отмена,
   проверь финалистов через `hotel_details()` и `hotel_rates()`. При
   `price.isFinalPrice=false` не называй остальные условия подтверждёнными.

При гибких датах используй `compare_hotel_prices()` для сравнения окон и бери
готовые дельты из ответа. `lowest observed` означает минимум только среди
полученных вариантов; сохраняй предупреждение при `meta.complete=false`.

## Карточки в чате

Не используй таблицу: фотографии и пояснения в ней читаются плохо. Сначала дай
одну строку с параметрами поиска и временем проверки, затем покажи каждый отель
отдельным блоком в порядке соответствия запросу:

```markdown
### 1. Название отеля ★★★★
![Название отеля](https://адрес-из-imageUrl)

**Цена из актуальной выдачи:** 00 000 ₽ за выбранный период
Рейтинг 0,0 · адрес · питание/отмена, только если подтверждены
Почему подходит: короткое фактическое объяснение.
```

Для изображения используй только HTTPS-значение `imageUrl`, которое вернул
`hotel_search()`. Не придумывай URL и не подставляй фотографии похожего отеля.
Если `imageUrl` отсутствует, пропусти Markdown-изображение и напиши «Фото в
источнике не предоставлено». Если клиент не отрисовал картинку, оставь тот же
URL как кликабельную ссылку «Открыть фото».

Не называй цену «за ночь» или «итоговой», если источник этого явно не
подтвердил: безопасная подпись — «цена из актуальной выдачи за выбранный период».
Не публикуй технические id в основном тексте. После карточек кратко укажи
неполноту выдачи, нефинальные цены и другие warnings.

Если пользователь просит перейти к оформлению, сначала вызови `hotel_rates()` и
покажи конкретные тарифы. Только после явного выбора тарифа можно вызвать
`hotel_checkout_url()` с его настоящим `book_hash` и `rate_confirmed=true`.
Checkout-ссылка ничего не бронирует и не оплачивает; финальные условия
пользователь проверяет на странице T-Bank.
